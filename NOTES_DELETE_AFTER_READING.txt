WHAT WAS THE ASSIGNMENT
-----------------------

ARTPARK gave you a small Python web service (FastAPI) in the app/ folder.
The service lets users type a natural language question about weather data
and get back a numeric answer with a source citation.

Example: user asks "what is the average temperature at S001?"
Service returns: { "answer": "...", "value": 24.5, "citations": ["reconciled_obs"] }

Your job was to take this rough prototype and make it production-ready.
Specifically they wanted 8 things:

1. A Docker container (deterministic build, tagged with git commit SHA)
2. Docker Compose with nginx as a reverse proxy handling HTTPS
3. A single deploy script that works for both localhost and AWS EC2,
   with automatic rollback if the deployment fails
4. A CI/CD pipeline (GitHub Actions) that lints, tests, builds, and pushes
5. ARCHITECTURE.md explaining 3 design choices about how the LLM is used
6. Data quality handling - show users when two sources disagree, never pick silently
7. Full observability (correlation IDs in logs, Grafana dashboard, Prometheus alerts)
8. One "surprise" - a failure mode the evaluators would likely miss


WHAT THE ORIGINAL CODE WAS DOING WRONG
---------------------------------------

- DATA_ROOT was hardcoded to "/Users/ankit/work/datalab/data" (someone else's Mac)
- When two data sources disagreed on the same record, it just picked the first one silently
- The LLM received raw CSV rows and computed the answer itself (not reproducible)
- Logging was plain text with no structure, no correlation IDs
- /health just returned {"status": "ok"} with nothing else
- No Docker setup, no CI, no observability at all
- requirements.txt had no version pins


WHAT WE BUILT
-------------

Data domain chosen: Environment
Three weather stations: Bangalore Central (S001), Hyderabad Begumpet (S002), Pune Lohegaon (S003)
Two data sources that disagree in schema and units:
  - Local station feed: temperature in Celsius, humidity as 0-100
  - API export: temperature in Fahrenheit, humidity as 0-1 decimal

New files created in app/:

  ctx.py
    Two Python ContextVars (correlation_id, query_id).
    These are set once per request in middleware and automatically appear
    in every log line for that request. No need to pass them around manually.

  metrics.py
    Seven Prometheus metrics:
    - analytics_requests_total (Counter) - request count by endpoint and status
    - analytics_request_duration_seconds (Histogram) - end-to-end latency
    - analytics_llm_duration_seconds (Histogram) - LLM time, separate for pass 1 and pass 2
    - analytics_cache_hits_total (Counter) - cache hit/miss/expired
    - analytics_response_quality_total (Counter) - full/degraded/error
    - analytics_data_disagreements_total (Counter) - source disagreements by field and station
    - analytics_data_version_info (Gauge) - unix timestamp of last data reload

  cache.py
    In-process Python dict cache.
    Cache key = SHA256(domain + data_version + normalized_question)
    Cache auto-invalidates when data_version changes (i.e. when data files change and service restarts)
    TTL = 3600 seconds as fallback

  reconciler.py
    Core data quality logic.
    Steps:
      1. Read local feed (Celsius, 0-100 humidity) - already canonical
      2. Read API export (Fahrenheit, 0-1 humidity) - convert: (F-32)*5/9 for temp, *100 for humidity
      3. Join on (station_id, date)
      4. Compare with tolerance: temp +-0.3C, humidity +-1 percentage point
      5. If outside tolerance: record disagreement with both values
      6. Use local feed as primary (no conversion rounding loss)
      7. Emit Prometheus counter for each disagreement
    Returns: reconciled_obs (clean rows) + disagreements list + summary

  logging_setup.py
    Replaced plain text logging with JSON structured logging.
    Every log line is one JSON object with correlation_id and query_id from ctx.py.
    This makes logs searchable by request ID in Grafana/Loki.

Modified files in app/:

  config.py
    Removed hardcoded Mac path. DATA_ROOT now reads from environment variable first,
    then falls back to ../data relative path. All config from env vars.

  data_loader.py
    Now calls reconciler.reconcile() for environment domain.
    Returns a tuple (tables, version_hash) instead of just tables.
    The version hash is SHA256 of all CSV file modification times.

  query_engine.py
    Replaced single-pass (LLM sees raw rows, computes answer) with two-pass:

    Pass 1: LLM receives table metadata only (schema, row counts, min/max/mean per column)
            LLM returns a JSON query spec: which table, which filters, what aggregation
            Example spec: {"table": "reconciled_obs", "filters": {"station_id": "S001"},
                           "aggregate": "mean", "target_col": "temp_c"}

    Pass 2: Python executes the spec deterministically (_execute function)
            Result is a scalar number (e.g. 24.5)
            LLM receives the result and formats a natural language answer with citations

    Why this is better:
    - Same question + same data = same answer every time (reproducible)
    - LLM never sees raw data rows (privacy, token efficiency)
    - The query spec is logged so any result can be reproduced

  providers.py
    Updated MockProvider to handle the two-pass system.
    It detects which pass it is by checking if "query planner" is in the system prompt.
    Returns appropriate mock JSON for each pass.

  main.py
    Added:
    - Correlation ID middleware (sets ctx vars, echoes X-Correlation-ID header back)
    - Prometheus timing middleware (records request duration)
    - Rich /health endpoint with 4 subsystem checks
    - Mounts /metrics on the FastAPI app (Prometheus scrapes this internally)

Infrastructure created:

  Dockerfile
    Multi-stage build. Stage 1 installs all Python deps into a virtualenv.
    Stage 2 copies only the virtualenv and app code. Data files baked in at /data.
    IMAGE_TAG build arg receives the git SHA from CI.
    Single worker (--workers 1) to keep in-process cache coherent.

  docker-compose.yml
    6 containers: app, nginx, prometheus, grafana, loki, promtail
    All on a shared "backend" Docker network
    nginx also on "frontend" network for external access

  infra/nginx/nginx.conf
    Listens on port 80 (HTTP, direct proxy for easy local testing)
    Listens on port 443 (HTTPS with self-signed cert)
    Blocks /metrics from external access
    Passes X-Correlation-ID header through to the app

  infra/prometheus/prometheus.yml + alerts.yml
    Scrapes app:8000/metrics every 15 seconds (direct, not through nginx)
    Three alert rules:
      ServiceDown - fires if service unreachable for 1 minute (critical)
      HighDegradedResponseRate - fires if >5% degraded responses for 2 minutes (warning)
      HighQueryLatency - fires if P95 latency >10s for 3 minutes (warning)

  infra/grafana/dashboards/analytics.json
    10-panel dashboard:
    Row 1: Request Rate, Error Rate, Cache Hit Rate
    Row 2: P95 End-to-End Latency, LLM Pass 1 P95, LLM Pass 2 P95
    Row 3: Response Quality stacked bar, Degraded Rate stat, Data Disagreements table
    Row 4: Live error logs from Loki

  deploy.sh
    Usage: bash deploy.sh localhost   or   bash deploy.sh aws
    Steps: validate env file exists -> validate required vars -> pull image ->
           capture current container ID for rollback -> docker compose up -d ->
           poll /health every 3 seconds for up to 60 seconds ->
           if fail: docker compose down + restart old image

  systemd/tabular-analytics.service
    For running the stack as a Linux service on EC2.
    Type=oneshot with RemainAfterExit=yes (correct pattern for docker compose)

  .github/workflows/ci.yml
    On every push to main:
    - lint: runs ruff check app/
    - test: runs pytest app/tests/ -v
    - build-push: builds Docker image tagged with git SHA, pushes to GHCR
    - deploy-staging: runs deploy.sh localhost in CI environment

THE ONE SURPRISE (most important design decision)
-------------------------------------------------

The original code returned HTTP 200 with "value": null when the LLM
returned malformed JSON. Standard monitoring (error rate, status codes)
would show zero errors. Users would see a "soft failure" - they get words
but no number. Operators would never know.

This happens when:
  - LLM is rate-limited and returns a partial/truncated response
  - Model changes and JSON schema drifts
  - Question triggers a long reasoning response that exceeds context window

Fix: every query response now has a "response_quality" field.
  "full" = LLM returned valid JSON with a numeric value
  "degraded" = LLM returned something but value is null
  "error" = could not parse LLM response at all

This is emitted as a Prometheus counter and there is a Grafana panel for it.
The HighDegradedResponseRate alert fires when >5% of responses are degraded.
A previously invisible failure mode is now a pageable signal.
